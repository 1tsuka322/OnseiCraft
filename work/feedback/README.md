# 反馈台账

> 后续的工作问题**都从这里来**。用户的反馈不直接改代码/知识表，先落成条目，
> 判清是「代码层」还是「语料层」，再走各自的出口。

## 1. 两类问题，两条出口

| 类别 | 台账 | 典型现象 | 出口 |
|---|---|---|---|
| **代码层** | [`ISSUES_CODE.md`](ISSUES_CODE.md) | 崩溃 / 闪退 / 界面错位 / 进度不动 / 卡住 / 装不上 / 路径错 / 同一输入两次结果不同 | 改代码 → 回归测试 → commit（必要时全库重跑受影响阶段） |
| **语料层** | [`ISSUES_CORPUS.md`](ISSUES_CORPUS.md) | 译法不对 / 术语不统一 / ASR 错字 / 断句时间轴 / 漏译 / 语气不符 / 人名前后不一致 | 改 `data/style/*.json` 或 `presets/` → `knowledge propose → validate → approve` → 全库 04-06 重跑 → promote |

**判类只看一件事：改哪里能修好它。**
改 `.py` / 安装包 / 界面能修 → 代码层；改术语表 / 错字表 / 提示词 / 切分规则能修 → 语料层。

⚠️ 有一类会横跨两边：**「这条字幕是空的」**。要先看是 04 切分切掉了（代码层）、
还是模型整句漏译（语料层）。判不清就先挂代码层，复现后再挪。

## 2. 目录

```
work/feedback/
├── README.md            本文件
├── ISSUES_CODE.md       代码层条目
├── ISSUES_CORPUS.md     语料层条目
├── inbox/               用户发来的原始 txt（原样丢进来，不改名）
└── processed/           已落成条目的原始 txt（归档，别删）
```

`inbox/` 与 `processed/` **不进版本库**（含用户内容）；两份 ISSUES 台账进库。

## 3. 一条反馈怎么走完

```
① 收     用户在 Studio「反馈日志」页导出 txt（自带：意见 + ASR 原文 + 修后原文 + 当前字幕）
          → 丢进 inbox/（或直接把 Studio 导出目录里的 txt 留着）
             ↓
② 消化   python work/scripts/feedback_ingest.py --apply
          解析每个 txt，按关键词初判类别，生成条目草稿追加到对应台账，
          原始 txt 移到 processed/
             ↓
③ 判类   人看一遍草稿，改分类、补「定位」（是识别错？翻译错？还是代码 bug？）
             ↓
④ 处理   代码层 → 改代码 + 跑该部的链路验证 + 全库回归
          语料层 → 提知识表提案（propose → validate → approve --by human --confirm）
             ↓
⑤ 关闭   台账里把状态改成「已修」，写清 commit / 提案 id / 影响的部数
```

## 4. 条目格式

```markdown
## L-003 · RJ01654115 / 03.先生は性処理ザーメンコキ捨て便所♪.mp3
- **来源**：`processed/feedback_RJ01654115_20261031_153225.txt`
- **用户意见**：「这里的语气词被翻得太生硬，应该是喘气不是『啊』」
- **时间点**：00:12.3
- **定位**：待复现 / 识别错 / 翻译错 / 切分错 / 代码 bug
- **处理**：
- **状态**：待处理 | 已定位 | 已修（commit abc1234）| 已证伪 | 不修（理由）
```

编号：`C-###`（代码）/ `L-###`（语料），只增不减，不复用。

## 5. 铁律

- **原始 txt 一律留档**（`processed/`），条目里必须能指回来源文件。
- **不在台账里直接写「已修」**，除非有 commit / 提案 id 可查。
- **一条反馈可以拆成多条条目**（同一份 txt 里既有译法问题又有界面问题）。
- **语料层的修改必须走知识表提案**，不许手改 `data/style/*.json` 后直接 promote
  （否则改了什么、影响哪些部，事后查不出来）。
