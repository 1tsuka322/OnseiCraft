# 架构与设计取舍

## 一句话

**把「模型判断」压缩到最少，把「确定性」铺满全链路。**
凡是能用查表/正则/对齐解决的，绝不交给模型；模型只做它真正擅长的那一小段。

这不是审美偏好，是踩出来的：让本地小模型「自己判断哪里错了」的路线，
实测召回 68%、**0 次弃权**（判不改的 6/7 是错的），受限协议格式通过率只有 48% —— 已用数字关闭。
现在能自动生效的全部是查表。

## 分层

```
┌─ 数据层 ────────────────────────────────────────────┐
│ audio → ASR(json) → 修正后 ASR → 初译 LRC → 成品 LRC │
│ 每层都是纯文件，可单独重跑、可单独 diff              │
└──────────────────────────────────────────────────────┘
┌─ 知识层 ────────────────────────────────────────────┐
│ 错字表 / 术语表 / 允许集 / 表记白名单 / 禁止表       │
│ 版本化 + 提案审批，绝不手改生产表                     │
└──────────────────────────────────────────────────────┘
┌─ 控制层 ────────────────────────────────────────────┐
│ pipeline.py：六阶段 + 指纹 + 断点续跑 + GPU 锁 + 门禁 │
└──────────────────────────────────────────────────────┘
```

## 五个关键决定

### 1. 产物是文件，不是内存状态

每个阶段读目录、写目录。好处：任何阶段都能单独重跑、单独对比、单独交给别人复核。
坏处：中间产物多。用 `runs/<run_id>/` 隔离，一个 run 一个目录，永不互相污染。

### 2. 指纹包含代码哈希

```python
fingerprint = hash(参数) + hash(输入文件) + hash(相关知识表) + hash(代码)
```

前三项是常识，第四项不是。动机很具体：曾经出现过「改了脚本、重跑、产物看起来没变，
实际是因为改的那个分支没走到」——没有代码哈希时，这种 bug 只能靠人肉记忆发现。

### 3. 人工修正用「锁」表达，不用「补丁脚本」

`data/locks/<project>.json` 存句级修正（时间戳 + 日文 + 中文）。
润色阶段写盘前先应用锁，所以**重跑永不冲掉人工修正**。
锁同时是「这句为什么是这样」的记录——比散落在对话里的解释可靠。

### 4. 知识表只能通过提案改

```
propose → validate（正例/反例逐条跑）→ approve（人工）→ 自动快照新版本
```

Agent 不得自批。理由：知识表是全链路唯一会「越改越错」的东西——
一条过宽的规则能静默污染几千行，而它不会让任何测试失败。

### 5. 门禁分「硬」和「参考」

- **硬门禁**（不过就 `gate_failed`，拒绝进生产）：格式、空字幕、知识表自检、回归
- **参考项**（只记数字）：扫描命中、截断审计、槽位守卫、覆盖层一致性

判据是**精度**：能稳定给出高精度结论的才配当硬门禁。精度 39% 的检查器如果当硬门禁，
团队会学会「无脑 `--force`」，那比没有门禁更糟。

## 为什么不用端到端模型

试过、也量化过：

| 路线 | 结果 |
|---|---|
| 微调本地模型做「改错判定」 | 召回 68%，0 弃权，判不改的多数是错的 |
| 受限 FLAG 协议（强制结构化输出） | 格式通过率 48%，外审量只降 24% |
| 端到端「音频→中文」 | 无法注入术语与风格，且不可局部修正 |

结论：**保持阶段可替换，每段用当前最强的方案，但绝不合并成黑盒。**

## 已知薄弱处

- 润色层仍会偶发截断（约每 25 句 1 句），靠截断审计发现，尚未自动修复。
- 拟声/气声的表外词识别是最大瓶颈，弱监督模型 AUC 0.918 但误报有地板，只能当排序器。
- 转写崩坏严重的作品（占比约 3%）需要人工逐轨重述，没有自动解法。
