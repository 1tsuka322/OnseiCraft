# 知识表

知识表是**查表类规则**的载体：错字修正、术语统一、允许集校验。
它们是全链路唯一会「越改越错」的东西——一条过宽的规则能静默污染几千行，
而且不会让任何测试失败。所以只能通过提案改。

## 四张表

| 文件 | 作用 | 谁用 |
|---|---|---|
| `asr_errata.json` | ASR 错字 → 正确写法 | `02_asr_fix` |
| `do_not_change.json` | 表记差异白名单（**不许**当错字改） | `02_asr_fix` |
| `glossary.json` | 术语 → 固定译法（进 prompt） | `03_translate` |
| `pin_sets.json` | 允许集（同一词的多个可接受译法） | `05_term_lock` |

运行时从 `data/style/` 读；公开仓库只带 `presets/` 里的公开副本。
查找顺序与风格库一致：`KIKOERU_STYLE` → `data/style` → `presets`。

## 错字条目格式

```json
{
  "ja": "错形",
  "fix": "正形",
  "mode": "auto",
  "ctx": ["上下文词 A", "上下文词 B"],
  "works": ["RJ0000001"],
  "legit": 0,
  "note": "为什么这是错字"
}
```

- `mode=auto`：错形不是正常词，可直接替换（仍过边界检查与表记白名单）
- `mode=guard`：**必须**命中 `ctx` 里的正向白名单之一，且作用域内、边界 OK，三者缺一不换
- `mode=review`：永不自动换，只进复核清单

### 为什么 `guard` 要用「正向白名单」而不是「负向断言」

早期用负向断言 `(?!...)` 排除误伤场景，结果每加一个反例就误杀一批真错字，
最后规则互相抵消。改成正向白名单后：**只在你确认过的语境里改**，
没覆盖到的新语境自动落进复核清单（`errata_new_ctx.json`），由人决定。

代价是召回低，但**误杀比漏改贵得多**：漏改一行是少改一行，误杀一行是把对的改成错的。

## 加条目的流程

```bash
P="python work/pipeline/pipeline.py"

# 1) 写提案（不要直接改生产表）
$P knowledge propose --file my_rule.json

# 2) 验证：正例/反例逐条跑，任一条不过就拒绝
$P knowledge validate --id <proposal_id>

# 3) 人工审批（必须 --by human --confirm）
$P knowledge approve --id <proposal_id> --by human --confirm

# 4) 审批后自动快照成新版本；失败会回滚
$P knowledge status
```

`approve` 会：加锁 → 幂等检查 → 去重 → 临时文件自检 → 原子替换 → 快照 → 失败回滚。

## 自检要求

每条规则必须带**反例**。只给正例的规则一定会误杀。

```bash
python work/scripts/errata_audit.py --test     # 逐条跑正例/反例
```

分两级，看你的语料覆盖：

| 语料 | 跑什么 | 输出 |
|---|---|---|
| 完整语料（基线 16 部 / ≥2 万段） | 结构断言 + **数值断言**（命中数/作品数/词频） | `44/44 通过` |
| 只有部分语料 | 只跑**结构断言**（mode 合法、ctx 正则可编译、无负向断言、无重复键） | `7/7 通过（结构断言）` + `SKIP 语料断言` |

⚠️ 数值期望（`n_hits` / `n_works` / `wrong_cf`）是**对着完整语料数出来的**。
语料不全时它们必然对不上——那不代表错字表坏了，所以脚本会 SKIP 而不是判失败。

## 术语表的边界

术语表管的是**固定译法**（同一个词永远这么译），不是**风格**。
风格（句长、标点、语气词密度）由 `data/style/` 里的规则与统计文件控制，两者不要混。

一条经验：术语条目宁可少而硬，不要多而软。
允许集（`pin_sets`）是给「同一个词在不同语域下有不同译法」用的——
把这种词钉成唯一译法，只会让译文变生硬。
