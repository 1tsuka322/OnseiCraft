# 参与开发

## 先跑起来（3 分钟）

```bash
python -m pip install -r requirements.txt
python work/pipeline/pipeline.py selftest      # 13 项，不需要任何数据
```

`selftest` 全过 = 环境没问题。它覆盖：阶段失败传播、断点续跑、指纹失效、
promote 拒绝遗留文件、锁的 token 语义、05 必须是独立目录。
**改任何代码之前先跑一遍，之后每改一次再跑一遍。**

## 开发约定

1. **不许静默改口径。** 影响产物的参数必须同时出现在四处：
   `pipeline_lib/paths.py` 的 `DEFAULTS`、`pipeline.json`、阶段 `params`、`Ctx` 的 env 注入。
   只改一处 = 指纹记的和实际跑的不一样，追溯链就断了。
2. **新增门禁先写自检。** 任何「判对错」的脚本，第一件事是证明它在**正确输入上返回 0**。
   历史教训：一个归一化 bug 让指标系统性偏高，自检却用同一条错路径，绕过了两年。
3. **改代码 = 改指纹。** 代码哈希进指纹是刻意的：脚本悄悄改了、产物看起来没变，是最难查的 bug。
4. **数据只读。** 不要把测试素材、音频、成品 LRC 提交上来（`.gitignore` 已挡住，但别绕过）。
5. **提交信息说清「为什么」。** 做了什么看 diff 就知道，为什么改必须写。

## 加一条新的确定性规则（最常见的贡献）

「确定性规则」= 查表或正则，不调模型。这类规则最受欢迎，因为它们可验证、可回滚。

1. 在 `docs/KNOWLEDGE.md` 里确认它属于哪张表（错字 / 术语 / 允许集）；
2. 写**正例 + 反例**各至少 3 条（反例是必须的：只给正例的规则一定会误杀）；
3. 跑 `python work/scripts/errata_audit.py --test`（或对应自检）；
4. PR 描述里贴自检输出原文。

## 加一个门禁

门禁必须回答三个问题：

- **它抓什么缺陷？** 举一个真实出现过的例子（脱敏后）。
- **为什么现有门禁抓不到？** 如果现有门禁能抓，就别加。
- **误报怎么办？** 阈值、白名单、或者降级成「参考项」（`hard: False`）。
